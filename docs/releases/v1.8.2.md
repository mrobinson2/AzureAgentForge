# v1.8.2 — release notes

> **Technical reference for contributors.** For the operational overview, start at [README](../../README.md) or [Architecture](../architecture.md).

[v1.8.1](v1.8.1.md) shipped agent peer identity. Deploying it to a real Azure
environment then found four defects — three of which had nothing to do with
identity and everything to do with the memory-governor never having been enabled
on a fresh subscription before. Each is fixed here with a test that catches it
without needing a deploy.

This release also completes the second deployment path: the self-hosted
(Mac-mini) stack can now set the same identity inputs Azure takes.

---

## Agent identity actually resolves now

1. **`PAPERCLIP_AGENT_SLUG` was never set — anywhere**
   ([#134](https://github.com/mrobinson2/AzureAgentForge/pull/134)). Upstream's
   `buildPaperclipEnv` gives a spawned agent `PAPERCLIP_AGENT_ID` (a UUID) and
   `PAPERCLIP_COMPANY_ID`, but no slug, and nothing in this repo supplied one.
   The memory helpers key identity off that variable, so every agent's writes
   collapsed onto a single fallback peer: memory could not be attributed per
   agent at all.

   `patch-adapter.mjs` now derives the slug from the agent's display name using
   the convention two other components already agree on
   (`services/watchdog/roster.py`'s name→slug map, `governor/profiles.py`'s
   keys): `Researcher`→`researcher`, `CostGuardian`→`cost-guardian`, `QA`→`qa`.
   A missing anchor fails the build rather than silently restoring one shared
   peer.

2. **The fallback peer held system write authority** (same PR). That fallback was
   `operator`, which `profiles.py` maps to the `SYSTEM` profile —
   `write: ALL_CLASSES`. So an agent whose identity failed to resolve did not
   merely lose attribution, it **inherited unrestricted write authority**, and
   admission's `profiles.can_write` check ran against the wrong, more privileged
   identity. A specialist limited to `task_scoped`/`ephemeral` could write any
   class. The fallback is now `unknown-agent`, deliberately absent from
   `DEFAULT_PROFILES` so it lands on the least-privilege `SPECIALIST` default,
   with a test that fails if anyone adds it back with authority.

## The governor could not start on a fresh deployment

3. **The image never contained its migrations**
   ([#135](https://github.com/mrobinson2/AzureAgentForge/pull/135)). The
   Dockerfile copied only `src/governor`, while `migrate.py` resolves
   `MIGRATIONS_DIR` relative to its own file — a path the image did not have. So
   `feature_flags` was never created and every flag lookup threw
   `UndefinedTableError`. Worse, `apply()` called that success: with an empty
   glob it logged `schema up to date (0 known)` seconds before the first error.
   Nothing to apply is only good news when there was something to check — an
   absent or empty directory now raises `MigrationsMissing`.

   Same PR: `memory_governor_image_tag` / `watchdog_image_tag` are now passed
   through the dev environment. They never were, so enabling the governor there
   fell back to `latest`, which this registry does not publish.

4. **The migration chain contradicted itself**
   ([#136](https://github.com/mrobinson2/AzureAgentForge/pull/136)). With the
   migrations finally shipping, applying them against a fresh database failed on
   `0003`: it seeds flags with `feature_flags.updated_by`, a column this chain's
   own `0001` never created — it exists only in the separate
   `infrastructure/migrations` chain. The chain worked wherever those had
   already run and broke the moment it ran alone, which is exactly what the
   governor does at startup. `0002a` ALTERs the column in idempotently, `0001`
   now matches the other chain, and two contract tests pin that every column a
   later INSERT references is created earlier in the *same* chain.

## Both deployment paths, same inputs

5. **Self-hosted parity**
   ([#133](https://github.com/mrobinson2/AzureAgentForge/pull/133)). v1.8.1
   wired only the Azure path. The self-hosted stack — the one most likely to
   hold legacy peers, since those sites predate the canonical-peer input — could
   not set either input at all.

   | `.env` (self-hosted) | Terraform (Azure) |
   |---|---|
   | `HONCHO_USER_PEER_ID` | `honcho_user_peer_id` |
   | `HONCHO_AGENT_PEER_IDS` | `honcho_agent_peer_ids` |
   | `HONCHO_PEER_ALIASES` | `honcho_peer_aliases` |

   Same strings, same parsing — a roster is portable between them verbatim. Only
   the transport differs. `deploy/mac-site/README.md` adds the warning specific
   to that topology: both sites share one managed PostgreSQL, so peer ids that
   differ between them fragment an identity across a failover, which is the
   failure this design exists to prevent. Treat them like the DB URL — both
   places or neither.

   Turnkey surfaces updated to match: the Forge Console gains two validated
   optional fields, `installer/core.py` renders them into `terraform.tfvars`
   (omitted entirely when empty, since an empty string would declare an *empty
   roster* and flag every write), `AI-ASSISTED-SETUP.md` gains Phase 9b covering
   both paths, and `terraform.tfvars.example` carries commented examples.

## Verification

Deployed to Azure dev and checked against the running artifacts, not just CI:

- All five migrations apply cleanly on a fresh database; governor startup
  completes with no `UndefinedTable`/`UndefinedColumn` errors.
- The deployed governor image, run with the live container's env, classifies the
  declared roster correctly: `researcher`/`cost-guardian`/`watchdog` →
  `known_agent`, `user` → `canonical_user`, and both `operator` and a
  per-channel peer → `unexpected` — the failure mode from item 2 is now visible
  instead of silent.
- The deployed paperclip image carries the slug injection in the adapter's
  compiled `execute.js`.

Suites: memory-governor 234, installer 93, skills 11, paperclip node 17.

## Upgrading

No migrations to run by hand — the governor applies its own overlay on startup,
which is now possible for the first time.

If you enable `memory_governor_enabled`, pin `memory_governor_image_tag` and
`watchdog_image_tag`; `latest` is not published. Identity resolution runs inside
admission, so it takes effect where governed memory is enabled
(`MEMORY_CLASSES_ENABLED`) — deploying this release does not turn that on.
