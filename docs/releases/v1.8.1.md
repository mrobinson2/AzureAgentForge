# v1.8.1 — release notes

> **Technical reference for contributors.** For the operational overview, start at [README](../../README.md) or [Architecture](../architecture.md).

One feature: the agent half of peer identity, and the identity map that goes with
it. [v1.8.0](v1.8.0.md) shipped the canonical *user* peer (A5) — one deploy-time
input naming the human principal. This adds the other side of the same set, so
the governor can tell a legitimate agent peer from a stray one.

Both new inputs default to empty, and empty means the previous behavior exactly.
No migrations. The memory-governor is off by default (`memory_governor_enabled`),
so a default deployment is unaffected either way.

---

## Agent peer identity

1. **`HONCHO_AGENT_PEER_IDS` — the expected agent set.** The canonical user peer
   answers "who is the human." Without the agent side, the only thing an
   unexpected-peer check can say is "not the human" — true of every legitimate
   agent self-lesson, and therefore useless. This input is a comma-separated list
   of agent slugs that are legitimate peers alongside the canonical user.

2. **`HONCHO_PEER_ALIASES` — the identity map at admission.** Comma-separated
   `alias=canonical` pairs, applied at `/admit` before anything reads the peers,
   so a known stray — a legacy name, a per-channel session peer — is rewritten as
   it arrives rather than accumulating. The alias never reaches storage, the
   dedup lookup, or a downstream event payload.

   This is item 1 of the production backstop
   [`memory-system.md` §18](../design/memory-system.md#18-identity-the-canonical-user-peer)
   describes. Item 2, the periodic re-consolidation sweep, remains designed and
   unimplemented.

3. **Classification and reporting.** `observer`, `observed`, and
   `created_by_peer` are each resolved through the alias map and classified as
   `canonical_user`, `known_agent`, `unexpected`, or `undeclared_roster`.
   Anything rewritten or unexpected emits a `memory_identity` event on the
   `agent_events` spine carrying the original peer, the resolved peer, and the
   classification — the operator's signal that a writer is minting peers nobody
   queries.

Three design choices worth stating, because each is a place this could have gone
wrong:

- **Report, never reject.** An unexpected peer is a config smell, not an attack.
  Refusing the write loses the memory while the misconfiguration that produced it
  is still in place — strictly worse than storing it and telling the operator.
- **Permissive when undeclared.** With no roster set, nothing is called a stray.
  A deployment that has not listed its agents would otherwise have every write
  flagged, and an alert that fires on everything is an alert nobody reads.
- **Fail open on bad config.** A malformed alias pair is skipped rather than
  fatal: this runs at the write choke point, and failing closed on our own config
  would lose every write for a typo. Alias resolution is one hop, so a cyclic
  config (`a=b,b=a`) terminates instead of hanging admission.

Agent self-lessons ([§10](../design/memory-system.md)) stay exempt from the
canonical-user rule, and now provably so: a declared agent observing itself
classifies as `known_agent` and emits nothing.

**Threading.** `governor/identity.py` (resolution + classification),
`memory/admission.py` (applied at the choke point), the memory-governor
Terraform module and dev environment, the root compose stack, and `.env.example`.

**Tests.** `tests/memory-governor/test_agent_identity.py` — 16 offline cases (no
DB, no HTTP) covering roster parsing, each classification, alias rewriting,
malformed and cyclic alias configs, the report-don't-reject contract, and the
agent-self-lesson exemption. Full governor suite: 229 passed.

## Upgrading

No migrations, no behavior change on default settings.

To turn it on, declare your roster and any known aliases:

```hcl
# terraform.tfvars
honcho_agent_peer_ids = "researcher,engineer,qa,watchdog"
honcho_peer_aliases   = "operator=user"
```

```bash
# .env (compose)
HONCHO_AGENT_PEER_IDS=researcher,engineer,qa,watchdog
HONCHO_PEER_ALIASES=operator=user
```

Discover the peers a deployment actually holds with `pc-honcho list-peers`
before writing either value — the roster should describe what is really there,
not what you intended.
